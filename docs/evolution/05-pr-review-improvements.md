## 1. 目标与边界

围绕 MewCode 的“告警 → 排查 → 修复 → 验证 → PR → 人工审查”流程，
补充独立修复审查、分析覆盖记录与评审反馈闭环。
保留交互式 CLI/TUI 与告警服务共享执行内核的设计。

已有的沙箱、任务恢复、告警去重、有界重试、token 统计、结构化 PR 和人工决策入口继续复用。
服务不获得远端 merge 权限，最终合并仍由人工决定。
PR-Agent 作为设计参考，不在本计划中直接引入运行时依赖。

## 3. 优先级与实施范围

### P1-A：独立修复审查

收益：发现“测试通过但修复不充分”及修复引入的副作用，为人工评审提供具体线索。
改动成本预估：中；涉及执行链、结构化结果、PR 展示和模型调用预算。

- 在修复验证通过后增加可配置审查步骤，使用独立上下文，避免沿用修复者的完整推理历史。
- 输入原始告警、根因判断、最终 diff、必要的关联代码、修复前后测试结果及仓库规则。
- 输出结构化问题：严重程度、文件与代码位置、触发条件、证据、建议补充的验证。
- 重点审查：是否解决原始告警、是否引入副作用、测试是否覆盖根因与边界条件。
- 复用现有调用与用量统计，单独记录审查 token、耗时及失败原因。
- 第一阶段作为提供给人工的附加结果，不因模型判断自动批准合并，也不默认触发返工。
- 审查失败、超时或覆盖不全时明确记录；不能显示成“审查通过”。

验收要求：

- “只隐藏异常”“无限重试”“删除校验以通过测试”等案例可用于检验审查质量。
- 清晰区分“未发现问题”“发现问题”“未完成审查”，并保留受审提交 SHA。
- 现有执行证据仍由服务生成，模型意见不能覆盖真实测试结果。
- 配置关闭时保留现有执行流程；启用时验证预算与失败处理行为。

### P1-B：diff 上下文组织与覆盖记录

收益：控制大变更的分析成本，避免未分析的文件被误认为已经检查。
改动成本预估：中；可先实现覆盖记录，再扩展分块与动态上下文。

- 将固定字符截断升级为文件/代码块级的预算分配；字符上限仍可作为资源保护。
- 为代码块补充所在函数、类及必要上下文，合并重叠区域，避免重复消耗预算。
- 对大变更分块处理，限制调用次数与总 token，汇总结果时去重。
- 保留删除代码的分析；删除鉴权、超时或清理逻辑可能正是风险来源。
- 记录完整分析、部分分析、未分析的文件及原因，区分二进制、过滤、预算不足等情况。
- 完整 diff/证据与模型输入分开存储；模型输入截断不应导致原始证据丢失。

验收要求：

- 大文件、多文件、纯删除、重命名和二进制变更均有明确处理结果。
- 覆盖记录与实际送入模型的内容一致，不因预算耗尽宣称完整审查。
- 动态上下文和分块总量受预算约束；结果关联固定 base/head SHA。
- 评估时记录审查召回、遗漏、token 与耗时，不能只比较输入长度。

### P2：GitHub 评审意见驱动返工

收益：人工直接在 PR 中评审，服务复用原 job 和工作区继续处理。
改动成本预估：中高；依赖事件接入、权限校验、幂等与提交版本校验。

- 优先接入明确的 changes-requested review，复用现有 `changes_requested` 状态与执行链。
- 绑定 PR、job、文件位置、评论及被审查的提交 SHA；保留原始意见作为审计证据。
- 验证 webhook 签名、仓库/PR 归属和评审者权限，不将任意评论视为执行授权。
- 对重放事件做幂等处理；忽略机器人自触发，过期提交上的意见需要明确处理策略。
- 将外部评论作为待分析数据，不允许其覆盖服务权限或沙箱规则。
- 保留现有 decision API，GitHub 事件只是新增入口。
- 返工必须重新验证并更新同一 PR；明确限制返工次数与累计预算，避免循环。

验收要求：覆盖有效修改请求、无权限请求、重复事件、过期 SHA、重启恢复和机器人循环。
同一事件不应创建多个任务或多个 PR，未授权事件不得触发执行。

### P3：持续审查结果与问题状态

收益：减少重复评论，让人工能看出问题是否已经解决。
改动成本预估：中；依赖结构化 finding 与审查覆盖记录。

- 更新同一份审查报告，记录受审 SHA 与运行状态，避免每次重跑新增整份评论。
- 为问题生成稳定标识，跟踪仍存在、已解决、人工拒绝和重新出现等状态。
- 行号漂移时结合代码锚点匹配，不能仅用当前行号标识同一个问题。
- 仅对确实重新分析的范围判断问题已解决；局部审查遗漏的问题保持原状态。
- 人工拒绝的问题保留理由；有新的代码证据时才重新提出。
- 行内评论必须验证位置属于相应 diff；无法可靠定位时保留在汇总报告。
- 沿用现有通知原则，仅在有意义的变化或需要人工处理时通知。

验收要求：重复运行不刷屏；部分覆盖不误关闭问题；发布失败可恢复；人工决定不被覆盖。

## 4. 建议开展顺序

1. 定义审查结果、提交版本与覆盖范围的数据结构，复用 job 审计和报告机制。
2. 实现 P1-B 的最小覆盖记录与预算控制，再接入 P1-A 的只提供意见模式。
3. 用评估集比较启用前后效果，决定是否扩展动态上下文、分块和受限自动返工。
4. 再开展 P2 GitHub 评审事件接入与 P3 持续问题跟踪。

第一轮交付范围为“独立修复审查 + 审查覆盖记录”。
是否增加状态机阶段、默认是否开启、失败是否阻塞发布、采用哪种模型，实施设计时另行确定。
独立上下文不要求立即增加新的模型提供商或多代理框架。

## 5. 验证与效果评估

- 复用现有告警回放框架，补充根因未解决、修复引入回归、删除安全逻辑、无问题修复和大 diff 案例。
- 为审查案例准备人工标注，统计有效发现、误报、漏报、覆盖范围、额外 token 和延迟。
- 区分检出的真实问题与模型给出的分数，不能用模型自评代替准确率。
- 离线测试覆盖结构化输出、预算、失败路径、版本绑定和幂等；外部模型和 GitHub 验证另行安排。
- 不把现有小样本回放结果当成新增审查能力的效果证据；新功能需独立建立基线。
- 如后续复制上游代码，先核对对应提交的许可证与署名要求。
