# 告警排查 SOP（incident triage）

无人值守场景下，**"改得对"比"改得快"重要**：一个错误的修复比不修复更糟。

## 步骤

1. **复现**：先让问题可复现——跑仓库测试、或按告警里的日志/堆栈定位到具体代码路径。
   复现不了就先如实记录"无法复现"，不要凭猜测改代码。
2. **定位根因**：读相关代码，找到真正的原因（不是症状）。写下你的判断依据：
   文件、函数、触发条件。
3. **最小修复**：只改必要的行。不顺手重构、不调整无关格式、不引入新依赖。
   如果最小修复做不到，说明原因。
4. **补/改测试**：修复后必须能通过仓库既有测试；若能补一条覆盖该 bug 的测试更好。
5. **自查**：按 `org-code-style` 清单逐项检查，并在最终报告里给出逐项结论。

## 硬性约束

- 只在当前工作目录（隔离 worktree）内改动。
- 不执行 `git push` / `git merge` / `git rebase`（远端）或任何 PR 命令——发布由服务层负责。
- 证据不足时：停手并明确说明缺什么信息（缺日志？缺复现步骤？），交回人工。
